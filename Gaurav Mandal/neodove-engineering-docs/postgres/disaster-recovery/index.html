PostgreSQL disaster recovery

Use this page first during a database incident. Stabilize the situation, preserve evidence, select one recovery path, and verify business behavior before declaring recovery.

First rule: prevent a second disaster Do not delete data directories, drop databases, detach volumes, promote multiple replicas, or restart the old primary after failover. One incident commander owns the recovery sequence.

Incident inputs

Fill the common values once. The health and validation commands below will update before you copy them.

First 10 minutes

  1. Declare the incident. Record the UTC start time, affected environment, reporter, and incident commander.
  2. Stop risky changes. Pause deployments, migrations, maintenance jobs, and automated restarts.
  3. Control writes. If data integrity is uncertain, put the application in maintenance/read-only mode.
  4. Preserve evidence. Keep the original machines, volumes, logs, WAL, and backups unchanged.
  5. Measure before acting. Collect the health snapshot below from each reachable database node.

Capture a health snapshot

Run on every reachable PostgreSQL node and label the output with its hostname.

date -u
hostname -f
sudo pg_ctlcluster 15 main status
df -h {{RUNBOOK_DATA_ROOT}}
sudo -iu postgres psql -d postgres -x -c "SELECT version(), pg_is_in_recovery(), now();"
sudo -iu postgres psql -d postgres -x -c "SHOW config_file; SHOW hba_file; SHOW data_directory;"
sudo -iu postgres psql -d postgres -x -c "SELECT pg_last_wal_receive_lsn(), pg_last_wal_replay_lsn(), pg_last_xact_replay_timestamp();"
sudo -iu postgres psql -d postgres -x -c "SELECT status, sender_host, slot_name, written_lsn, flushed_lsn, latest_end_lsn, last_msg_receipt_time FROM pg_stat_wal_receiver;"
sudo -iu postgres psql -d postgres -x -c "SELECT client_addr, state, sync_state, sent_lsn, write_lsn, flush_lsn, replay_lsn FROM pg_stat_replication;"

The WAL receiver view is populated on a connected standby; the replication view is populated on a primary with connected standbys. Empty results help identify the node's role or a broken connection. Record all output and do not hide unexpected errors.

Choose exactly one recovery path

Observed failureRecovery pathDo not do
Primary is healthy; one replica failedRebuild only the failed replicaDo not promote the failed replica.
Primary is lost; one replica is current and healthyControlled replica promotion belowDo not allow the old primary to return and accept writes.
Accidental delete or bad migrationRestore into an isolated database; use PITR only if WAL archive existsDo not assume the replica has clean data.
Database files or volume are corruptedRestore a verified backup to new storageDo not overwrite the damaged source before evidence is captured.
Credentials or host compromisedIsolate host, restore on clean infrastructure, rotate all credentialsDo not trust binaries, configuration, or private keys from the compromised host.
No verified backup and no healthy replicaPreserve everything and escalate to PostgreSQL recovery specialistsDo not improvise file deletion, reset WAL, or forced startup.

Controlled promotion of one replica

Promotion is irreversible for this topologyProceed only after the old primary is fenced from application traffic and cannot accept writes. Promotion creates a new timeline; the old primary must later be rebuilt as a replica.

1. Fence the old primary

  • Application writes are stopped or routed away from the old primary.
  • The old primary is stopped, isolated by network controls, or confirmed unavailable.
  • Exactly one standby has been selected as the promotion candidate.
  • The incident commander approved the expected data-loss window.

2. Measure the candidate standby

date -u
hostname -f
sudo -iu postgres psql -d postgres -x -c "SHOW config_file; SHOW hba_file; SHOW data_directory;"
sudo -iu postgres psql -d postgres -x -c "SELECT pg_is_in_recovery(), pg_last_wal_receive_lsn(), pg_last_wal_replay_lsn(), pg_last_xact_replay_timestamp();"
sudo -iu postgres psql -d postgres -x -c "SELECT status, sender_host, slot_name, latest_end_lsn, last_msg_receipt_time FROM pg_stat_wal_receiver;"

Record the last replay LSN and transaction timestamp. If they are older than the accepted recovery point, stop and choose a better recovery source.

3. Promote the selected standby

sudo pg_ctlcluster 15 main promote
sudo pg_ctlcluster 15 main status
sudo -iu postgres psql -d postgres -c "SELECT pg_is_in_recovery(), pg_current_wal_lsn(), now();"

Expected: pg_is_in_recovery() returns f.

4. Validate before restoring writes

sudo -iu postgres psql -d postgres -c "SELECT datname, pg_size_pretty(pg_database_size(datname)) FROM pg_database ORDER BY pg_database_size(datname) DESC;"
sudo -iu postgres psql -d postgres -c "SELECT count(*) AS invalid_indexes FROM pg_index WHERE NOT indisvalid;"
sudo journalctl -u postgresql@15-main --since "{{RUNBOOK_JOURNAL_SINCE}}" --no-pager

Update the approved application database endpoint to this host, run read-only smoke tests, then restore writes gradually while monitoring database and application errors.

Accidental change and point-in-time recovery

PITR requires a base backup plus an unbroken sequence of archived WAL that was configured and tested before the incident. If either is missing, do not claim point-in-time recovery is available.

  1. Record the last known good UTC time and the bad-change time from application and database evidence.
  2. Preserve the current timeline, base backups, and WAL archive.
  3. Recover into isolated infrastructure to a target time before the bad change.
  4. Validate critical rows and business totals; adjust the target using a fresh isolated recovery if needed.
  5. Plan cutover separately with write freeze, endpoint switch, and rollback criteria.
Environment-specific configuration requiredArchive location, restore command, encryption, retention, and recovery target settings must match the approved backup platform. Do not invent an archive_command during an incident.

After service is restored

  • Critical business queries and application flows are verified.
  • Error rate, connections, disk, WAL, replication, and latency are monitored.
  • The old primary remains isolated and is scheduled to be rebuilt from the new primary.
  • A new backup is created from the recovered timeline after stability is confirmed.
  • Timeline, commands, decisions, data loss, and follow-up actions are recorded.
  • This runbook is updated with every lesson from the incident.
