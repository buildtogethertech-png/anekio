Set up PostgreSQL PITR with AWS Backup + S3 WAL

For staging, use AWS Backup EBS snapshots as the base copy and PostgreSQL WAL archiving to S3 for point-in-time recovery. This protects against accidental deletes, bad migrations, and corruption that replicas will also receive.

PITR is not complete until a restore test passes Seeing WAL files in S3 is not enough. A recovery machine must restore a base backup, replay WAL, stop at a target time, and open cleanly.

Current staging strategy

This is the cheaper staging pattern NeoDove is using for the first drill:

PartUseStatus for stagingCost note
AWS Backup EBS snapshotBase copy of the PostgreSQL diskRequired, every 12 hoursCosts start after the backup plan has a resource assignment and recovery points are created. Snapshot storage is incremental, not full disk every run.
S3 WAL archiveRecover from latest snapshot time to exact target timeRequired, continuousSmall S3 storage + PUT request cost, grows with database write volume and retention days.
PostgreSQL pg_basebackup to S3Postgres-native base backupOptional, not needed for this staging planDuplicates storage cost if AWS Backup is already the base copy.
AWS Backup PITR checkboxAWS-managed continuous backup for supported resourcesKeep OFF for this PostgreSQL-on-EC2 staging planCan add extra cost and does not replace PostgreSQL WAL archive design here.
Cold storage / cross-region / air-gapped vaultLong-term or stronger isolationKeep OFF for cheapest staging drillCan increase cost or minimum retention commitments.
Important mental model AWS Backup gets you back to the snapshot time. S3 WAL archive moves PostgreSQL forward from that snapshot to the exact recovery time. Without WAL, a 12:00 snapshot restored at 14:47 loses 2h47m of data.

Preconditions

  • The PostgreSQL primary is confirmed and reachable.
  • AWS CLI is installed on the database host and can authenticate without putting keys in shell history.
  • The S3 bucket is private, encrypted, versioned, and access is least privilege.
  • A PostgreSQL restart window is approved because archive_mode requires restart.
  • A separate restore-test host or volume is available.

Verify primary and active paths

hostname -f
sudo -iu postgres psql -d postgres -c "SELECT version(), pg_is_in_recovery();"
sudo -iu postgres psql -d postgres -c "SHOW config_file; SHOW hba_file; SHOW data_directory;"

pg_is_in_recovery() must be f on the primary where WAL archiving is enabled.

Verify AWS identity and S3 access

command -v aws

The caller must be the approved DB-host role/user and the bucket must be reachable.

1. Install AWS CLI on the database host

Run this on the PostgreSQL primary. The Ubuntu package is enough for S3 upload/archive commands. After install, copy the printed path into the AWS CLI binary path input above if it is different.

command -v aws || true
sudo apt-get update
sudo apt-get install -y awscli
command -v aws
aws --version

If the package is unavailable or your team requires AWS CLI v2 from AWS, use the official installer. First check CPU architecture; installing the wrong zip causes cannot execute binary file: Exec format error.

uname -m
file /bin/bash

For Intel/AMD instances where uname -m prints x86_64:

sudo apt-get update
sudo apt-get install -y curl unzip
curl "https://awscli.amazonaws.com/awscli-exe-linux-x86_64.zip" -o "/tmp/awscliv2.zip"
unzip -q /tmp/awscliv2.zip -d /tmp
sudo /tmp/aws/install --update
/usr/local/bin/aws --version

For Graviton/ARM instances where uname -m prints aarch64:

sudo apt-get update
sudo apt-get install -y curl unzip
curl "https://awscli.amazonaws.com/awscli-exe-linux-aarch64.zip" -o "/tmp/awscliv2.zip"
unzip -q /tmp/awscliv2.zip -d /tmp
sudo /tmp/aws/install --update
/usr/local/bin/aws --version

If the wrong architecture was already installed, remove it and rerun the correct installer:

sudo /usr/local/aws-cli/v2/current/dist/aws --version || true
sudo unlink /usr/local/bin/aws || true
sudo unlink /usr/local/bin/aws_completer || true
sudo mv /usr/local/aws-cli "/usr/local/aws-cli.wrong-arch-$(date -u +%Y%m%dT%H%M%SZ)" || true
uname -m
Use an IAM role if this is EC2Do not put permanent AWS access keys in shell history or root files. Prefer an EC2 instance profile/role with the S3 policy in step 4. In AWS Console: EC2 -> Instances -> select DB host -> Actions -> Security -> Modify IAM role.

After attaching the role, verify credentials as the normal login user and as postgres:

{{PITR_AWS_BIN}} sts get-caller-identity
sudo -iu postgres {{PITR_AWS_BIN}} sts get-caller-identity
sudo -iu postgres {{PITR_AWS_BIN}} configure list

If the postgres check fails, fix the instance role or AWS CLI access before continuing. Avoid sudo aws configure; that configures root, not PostgreSQL.

2. Create the S3 bucket safely

Bucket settings to use in AWS Console: block all public access, bucket owner enforced, default encryption SSE-S3 or SSE-KMS, versioning enabled, lifecycle retention reviewed, and no public bucket policy.

{{PITR_AWS_BIN}} s3api create-bucket \
  --bucket "{{PITR_BUCKET}}" \
  --region "{{PITR_REGION}}" \
  --create-bucket-configuration LocationConstraint="{{PITR_REGION}}"

{{PITR_AWS_BIN}} s3api put-public-access-block \
  --bucket "{{PITR_BUCKET}}" \
  --public-access-block-configuration BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true

{{PITR_AWS_BIN}} s3api put-bucket-versioning \
  --bucket "{{PITR_BUCKET}}" \
  --versioning-configuration Status=Enabled

{{PITR_AWS_BIN}} s3api put-bucket-encryption \
  --bucket "{{PITR_BUCKET}}" \
  --server-side-encryption-configuration '{"Rules":[{"ApplyServerSideEncryptionByDefault":{"SSEAlgorithm":"AES256"}}]}'

If the region is us-east-1, create the bucket without --create-bucket-configuration. For other regions, keep the region constraint.

If you need Object LockObject Lock must be enabled when creating the bucket. Use it for production if the organization requires write-once retention against accidental or malicious deletion.

4. Create least-privilege IAM permissions

Choose role, not user, for EC2 For a PostgreSQL server running on EC2, create an IAM role with trusted entity AWS service and use case EC2. Do not create an IAM user for this case. IAM users create long-lived access keys, which are easier to leak and harder to rotate safely.

Create an EC2 IAM role for database hosts and attach it to the instance when PITR is enabled. For the primary, read-only is not enough: PostgreSQL must continuously upload WAL files. Use a separate read-only role only for restore-test hosts that never upload WAL.

RoleAttach toNeedsWhy
{{PITR_IAM_NAME}}-writerPrimary DB hostList, read, write, multipart uploadArchive WAL files to S3.
{{PITR_IAM_NAME}}-readerRestore-test or recovery-only hostList and readDownload base backup and WAL for PITR restore.

Attach permissions to the instance role if possible. Prefer instance role over long-lived access keys on the server.

AWS Console steps for EC2 role

  1. Open IAM -> Roles -> Create role.
  2. On Select trusted entity, choose AWS service.
  3. Under Service or use case, choose EC2, then continue.
  4. Create or select the reviewed S3 policy below. Use writer policy for DB hosts, reader policy for restore-only hosts.
  5. Name the role {{PITR_IAM_NAME}}-writer for primary hosts or {{PITR_IAM_NAME}}-reader for restore-only hosts.
  6. Attach the role to EC2: EC2 -> Instances -> select DB host -> Actions -> Security -> Modify IAM role.
  7. Back on the server, run the access test in step 5 as the postgres user.

Writer policy for DB hosts

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ListPitrBucket",

5. Test S3 access as the postgres user

On the primary/backup host with the writer role, both upload and list must work:

sudo -iu postgres {{PITR_AWS_BIN}} sts get-caller-identity
sudo -iu postgres {{PITR_AWS_BIN}} s3 cp /etc/hostname "{{PITR_ROOT_URI}}/access-test/hostname-$(date -u +%Y%m%dT%H%M%SZ)"
sudo -iu postgres {{PITR_AWS_BIN}} s3 ls "{{PITR_ROOT_URI}}/access-test/"

On a restore-only host with the reader role, list and download must work, but upload should fail:

sudo -iu postgres {{PITR_AWS_BIN}} sts get-caller-identity
sudo -iu postgres {{PITR_AWS_BIN}} s3 ls "{{PITR_ROOT_URI}}/"
sudo -iu postgres {{PITR_AWS_BIN}} s3 cp "{{PITR_ROOT_URI}}/access-test/" /tmp/pitr-access-test --recursive

If this fails, fix IAM or AWS CLI configuration before touching PostgreSQL archiving.

6. Enable WAL archiving on the primary

The archive command below avoids overwriting an existing WAL object. archive_mode needs a PostgreSQL restart.

sudo -iu postgres psql -d postgres -c "ALTER SYSTEM SET archive_mode = 'on';"
sudo -iu postgres psql -d postgres -c "ALTER SYSTEM SET archive_timeout = '60s';"
sudo -iu postgres psql -d postgres -c "ALTER SYSTEM SET archive_command = '{{PITR_AWS_BIN}} s3api head-object --bucket {{PITR_BUCKET}} --key {{PITR_PREFIX}}/{{PITR_ENV}}/wal/%f >/dev/null 2>&1 || {{PITR_AWS_BIN}} s3 cp %p s3://{{PITR_BUCKET}}/{{PITR_PREFIX}}/{{PITR_ENV}}/wal/%f';"
sudo pg_ctlcluster 15 main restart
sudo pg_ctlcluster 15 main status
sudo -iu postgres psql -d postgres -c "SHOW archive_mode; SHOW archive_command; SHOW archive_timeout;"
sudo -iu postgres psql -d postgres -c "SELECT pg_switch_wal();"
sleep 10
sudo -iu postgres psql -d postgres -c "SELECT archived_count, failed_count, last_archived_wal, last_archived_time FROM pg_stat_archiver;"
sudo -iu postgres {{PITR_AWS_BIN}} s3 ls "{{PITR_WAL_URI}}/" | tail
Stop conditionIf failed_count increases or no WAL appears in S3, do not continue. Fix archive authentication, bucket permissions, region, or network access first.

7. Create AWS Backup base-copy plan

For staging, AWS Backup is the base-copy mechanism. Create snapshots for the database EBS volume, then use archived WAL from S3 to recover to the exact time.

Cost starts here After a resource assignment is added, AWS Backup will create recovery points on schedule. EBS snapshots are incremental, so every 12-hour run does not upload the full volume again, but retained changed blocks still cost money. Keep staging retention short.

AWS Console settings

  1. Open AWS Backup -> Vaults -> Create vault. Use vault name {{AWS_BACKUP_VAULT}}. Use a normal backup vault for staging.
  2. Open AWS Backup -> Backup plans -> Create backup plan.
  3. Choose Build a new plan if no template fits. Name it {{AWS_BACKUP_PLAN}}.
  4. Add rule name {{AWS_BACKUP_RULE}}.
  5. Frequency: every 12 hours. For staging, start at 00:30 Asia/Calcutta or another quiet time.
  6. Backup window: Start within 8 hours. Complete window: 1 day is enough for staging.
  7. Lifecycle: keep retention at {{AWS_BACKUP_RETENTION_DAYS}} days for cheapest staging drill.
  8. Leave Point-in-time recovery (PITR) unchecked here. PostgreSQL PITR is handled by S3 WAL archive.
  9. Leave cold storage, cross-region copy, logically air-gapped vault, and malware scanning off unless the team explicitly wants the extra cost.
  10. Assign resources: choose resource type EBS, then select volume {{AWS_BACKUP_VOLUME_ID}}.
Do not select all resources For staging cost control, assign only the PostgreSQL data EBS volume. Selecting all resources can unexpectedly back up unrelated volumes and increase cost.

Verify the plan after creating it

printf 'Backup plan: {{AWS_BACKUP_PLAN}}\nRule: {{AWS_BACKUP_RULE}}\nVault: {{AWS_BACKUP_VAULT}}\nVolume: {{AWS_BACKUP_VOLUME_ID}}\nRetention: {{AWS_BACKUP_RETENTION_DAYS}} days\n'

In AWS Console, check AWS Backup -> Backup plans -> {{AWS_BACKUP_PLAN}}. It must show one backup rule and one resource assignment for volume {{AWS_BACKUP_VOLUME_ID}}.

First scheduled backup depends on the rule start time and backup window. If you need a restore drill today, create one on-demand backup from the assigned volume.

On-demand backup also costs Use it only when you need a same-day drill. Keep its retention short, same as staging.

8. Configure S3 WAL lifecycle retention

Lifecycle should keep WAL for longer than the oldest AWS Backup snapshot you might restore. If AWS Backup retention is 2 days, keep S3 WAL at least 3 days so there is overlap.

{
  "Rules": [
    {
      "ID": "ExpireOldPitrObjects",
      "Status": "Enabled",
      "Filter": {
        "Prefix": "{{PITR_PREFIX}}/{{PITR_ENV}}/"
      },
      "Expiration": {
        "Days": {{PITR_RETENTION_DAYS}}
      },
      "NoncurrentVersionExpiration": {
        "NoncurrentDays": {{PITR_RETENTION_DAYS}}
      }
    }
  ]
}

Save this as a reviewed lifecycle JSON, then apply it:

nano pitr-lifecycle.json
{{PITR_AWS_BIN}} s3api put-bucket-lifecycle-configuration \
  --bucket "{{PITR_BUCKET}}" \
  --lifecycle-configuration file://pitr-lifecycle.json

{{PITR_AWS_BIN}} s3api get-bucket-lifecycle-configuration --bucket "{{PITR_BUCKET}}"

9. Monitor WAL archiving and AWS Backup

sudo -iu postgres psql -d postgres -c "SELECT archived_count, failed_count, last_archived_wal, last_archived_time, now() - last_archived_time AS archive_age FROM pg_stat_archiver;"
sudo -iu postgres {{PITR_AWS_BIN}} s3 ls "{{PITR_WAL_URI}}/" | tail
sudo -iu postgres psql -d postgres -c "SELECT pg_switch_wal();"

Alert if failed_count increases, archive_age is too old, or S3 object count stops changing during write activity.

In AWS Console, check AWS Backup -> Jobs and AWS Backup -> Backup vaults -> {{AWS_BACKUP_VAULT}}. The latest recovery point for {{AWS_BACKUP_VOLUME_ID}} should be completed.

10. Tomorrow drill: restore AWS Backup snapshot, then replay S3 WAL

Do not test PITR on the only working database directory. Restore to a separate EC2 host or separate EBS volume.

AWS Console restore steps

  1. Open AWS Backup -> Backup vaults -> {{AWS_BACKUP_VAULT}}.
  2. Choose a completed recovery point for EBS volume {{AWS_BACKUP_VOLUME_ID}} that is older than {{PITR_TARGET_TIME}}.
  3. Click Restore.
  4. Restore as a new EBS volume in the same Availability Zone as the restore-test EC2 instance.
  5. Attach the restored volume to the restore-test EC2 instance as a secondary disk. Do not detach or overwrite the live primary volume.
  6. Mount it and confirm it contains the PostgreSQL data directory before changing recovery settings.
Stop condition If you are on the live primary host or the only working database directory, stop. PITR drills must happen on separate infrastructure.

On the restore host, identify and mount the restored volume. Replace /dev/nvme1n1 with the restored disk from lsblk.

lsblk -f
sudo install -d -m 755 /mnt/aws-backup-restore
sudo mount /dev/nvme1n1 /mnt/aws-backup-restore
sudo find /mnt/aws-backup-restore -maxdepth 5 -name PG_VERSION -print

Then stop PostgreSQL before replacing the restore host's empty data directory:

sudo pg_ctlcluster 15 main stop
RUNBOOK_DATA_DIR="$(sudo -iu postgres psql -d postgres -Atqc "SHOW data_directory;" 2>/dev/null || echo /var/lib/postgresql/15/main)"
RUNBOOK_OLD_DATA="${RUNBOOK_DATA_DIR}.before-pitr-restore-$(date -u +%Y%m%dT%H%M%SZ)"
sudo mv "$RUNBOOK_DATA_DIR" "$RUNBOOK_OLD_DATA"
sudo install -d -o postgres -g postgres -m 700 "$RUNBOOK_DATA_DIR"

Copy the restored snapshot's PostgreSQL data directory into $RUNBOOK_DATA_DIR. Adjust the mounted path after checking the disk.

sudo rsync -aHAX --numeric-ids /mnt/aws-backup-restore/RESTORED_POSTGRES_DATA_DIR/ "$RUNBOOK_DATA_DIR/"
sudo chown -R postgres:postgres "$RUNBOOK_DATA_DIR"
sudo chmod 700 "$RUNBOOK_DATA_DIR"

Add recovery settings for PostgreSQL 15:

sudo -iu postgres tee "$RUNBOOK_DATA_DIR/postgresql.auto.conf" > /dev/null <<'EOF'
restore_command = '{{PITR_AWS_BIN}} s3 cp s3://{{PITR_BUCKET}}/{{PITR_PREFIX}}/{{PITR_ENV}}/wal/%f %p'
recovery_target_time = '{{PITR_TARGET_TIME}}'
recovery_target_action = 'promote'
EOF
sudo -iu postgres touch "$RUNBOOK_DATA_DIR/recovery.signal"
sudo chmod 700 "$RUNBOOK_DATA_DIR"
sudo pg_ctlcluster 15 main start
sudo pg_ctlcluster 15 main status
sudo -iu postgres psql -d postgres -c "SELECT pg_is_in_recovery(), pg_current_wal_lsn(), now();"
sudo journalctl -u postgresql@15-main --since "30 minutes ago" --no-pager

Expected: PostgreSQL replays WAL, reaches the target time, promotes, and opens. Verify the bad change is absent and good data is present.

Optional: PostgreSQL-native base backup to S3

This is not required for the current cheapest staging plan because AWS Backup already provides the base copy. Use this later only if the team wants PostgreSQL-native backups with tools like pgBackRest/Barman, or wants an extra base copy outside AWS Backup.

Cost note Running this in addition to AWS Backup duplicates base-backup storage. For staging, keep it off unless you are testing the backup tool itself. 
PITR_BACKUP_STAMP="$(date -u +%Y%m%dT%H%M%SZ)"
PITR_BACKUP_DIR="{{PITR_LOCAL_BACKUP_DIR}}/base_${PITR_BACKUP_STAMP}"

sudo install -d -o postgres -g postgres -m 700 "{{PITR_LOCAL_BACKUP_DIR}}"
sudo -iu postgres /usr/lib/postgresql/15/bin/pg_basebackup \
  --pgdata="$PITR_BACKUP_DIR" \
  --format=tar \
  --gzip \
  --wal-method=none \
  --checkpoint=fast \
  --progress \
  --verbose

sudo -iu postgres {{PITR_AWS_BIN}} s3 cp "$PITR_BACKUP_DIR" "{{PITR_BASE_URI}}/${PITR_BACKUP_STAMP}/" --recursive
sudo -iu postgres {{PITR_AWS_BIN}} s3 ls "{{PITR_BASE_URI}}/${PITR_BACKUP_STAMP}/"

Completion checklist

  • S3 bucket is private, encrypted, versioned, and lifecycle reviewed.
  • The postgres user can upload/list required S3 paths with least-privilege access.
  • WAL archiving is enabled, files arrive in S3, and failed_count is stable.
  • AWS Backup plan {{AWS_BACKUP_PLAN}} protects only the intended EBS volume {{AWS_BACKUP_VOLUME_ID}}.
  • At least one AWS Backup recovery point completed in vault {{AWS_BACKUP_VAULT}}.
  • A PITR restore test to a target time passed on separate infrastructure.
