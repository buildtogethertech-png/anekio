Create a machine deploy key

Give each deployment machine a unique, read-only SSH identity for the exact repository it needs.

Private key boundaryOnly the .pub public key goes into GitLab. The private key never leaves the deployment machine and must never appear in chat, tickets, CI logs, or documentation.

Policy

  • One unique key per machine and repository access boundary.
  • Read-only access by default; enable write only for an approved push requirement.
  • Never copy one private key to another machine.
  • Record machine, environment, repository, responsible engineer, creation, expiry, and verification dates.
  • Revoke immediately when a machine is retired, compromised, or changes owner.

A GitLab Deploy Key uses SSH. A GitLab Deploy Token is a separate HTTPS username/token credential.

1. Create the key as the deployment user

Use the actual Linux user that runs deployment or git pull. This is usually ubuntu on the server. Do not create the key as root unless root is the approved deployment user.

whoami
install -d -m 700 "$HOME/.ssh"
ssh-keygen -t ed25519 \
  -C "staging-machine" \
  -f "$HOME/.ssh/neodove-admin-staging"
chmod 600 "$HOME/.ssh/neodove-admin-staging"
chmod 644 "$HOME/.ssh/neodove-admin-staging.pub"
stat -c '%U:%G %a %n' "$HOME/.ssh/neodove-admin-staging" "$HOME/.ssh/neodove-admin-staging.pub"

If this key already exists, stop and check whether this machine already has a deploy key. Do not overwrite an existing private key unless rotation is approved. Do not use sudo. For approved unattended deployment, use an empty passphrase only when no agent or secret manager is available, then compensate with least privilege, strict permissions, expiry, and rotation.

2. Add only the public key to GitLab

cat "$HOME/.ssh/neodove-admin-staging.pub"
  1. Open arpit.neodove/neodove-admin.
  2. Go to Settings → Repository → Deploy Keys.
  3. Use title staging-machine | neodove-admin | read-only | YYYY-MM-DD.
  4. Paste the complete public key and leave write access disabled.
  5. Set an expiry date and save.

3. Bind the repository to this key

The Host alias below is the fake hostname used only by SSH config. The remote URL must use the same alias after git@.

nano "$HOME/.ssh/config"
Host gitlab-neodove-admin-staging
    HostName gitlab.com
    User git
    IdentityFile ~/.ssh/neodove-admin-staging
    IdentitiesOnly yes
chmod 600 "$HOME/.ssh/config"
git remote set-url origin git@gitlab-neodove-admin-staging:arpit.neodove/neodove-admin.git
git remote -v
ssh -G gitlab-neodove-admin-staging | sed -n '/^hostname /p;/^user /p;/^identityfile /p'
Why the remote starts with git@ GitLab SSH URLs always use the Linux user git. The part after @ must match your SSH Host alias. So this pair is correct: Host gitlab-neodove-admin-staging and git@gitlab-neodove-admin-staging:arpit.neodove/neodove-admin.git.

If you want the shorter alias gitlab

Use this only when the machine needs one GitLab identity. If one machine pulls multiple repos with different deploy keys, use unique aliases like gitlab-neodove-admin-staging.

Host gitlab
    HostName gitlab.com
    User git
    IdentityFile ~/.ssh/neodove-admin-staging
    IdentitiesOnly yes
git remote set-url origin git@gitlab:arpit.neodove/neodove-admin.git
git remote -v

4. Verify host and repository access

Compare the first connection fingerprint with GitLab.com's published SSH fingerprints before accepting it.

ssh -T git@gitlab-neodove-admin-staging
git ls-remote origin
git pull origin staging

If Git asks for an HTTPS username, origin still uses HTTPS. If it reports Permission denied (publickey), inspect key selection with:

ssh -vT git@gitlab-neodove-admin-staging
