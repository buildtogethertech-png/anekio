Anekio System Design

Anekio is an India-first school product with one Expo app for web, Android, and iOS, and one Express API. This document captures the intended system shape, the database boundaries, and the rules to follow when making schema or feature changes.

Ticket: KAN-100 Updated: 2026-09-11 UI: Expo only API: Express Database: Prisma + SQLite

Architecture At A Glance

Expo Client

The mobile/web app lives under mobile/. Screens in mobile/app/(app)/ route into mobile/components/portal-body.tsx, which selects the portal-specific board by nav key.

  • Portals: office, teacher, parent, student.
  • Route by mobile/lib/paths.ts keys, not stale href values.
  • Mobile must not import root lib/ directly.

Express API

The API entry is server/index.ts. Product reads are gathered by GET /api/v1/record; product writes are dispatched through POST /api/v1/act.

  • Write operations are op cases in lib/run-act.ts.
  • Core mutations sit in lib/core-actions.ts and lib/core-office.ts.
  • Public pay, invoice, document, and school website routes are Express HTML routes.

Data Layer

The Prisma schema in prisma/schema.prisma is the source of truth. This project uses prisma db push, not migrations.

  • Prisma client is cached by lib/prisma.ts.
  • After schema changes, restart npm run api.
  • Seed scripts overwrite demo login exports.

Primary Runtime Flow

1. Login

/api/v1/login and OTP/password helpers issue the app token.

2. Session

/api/v1/me returns the user, portal, permissions, and nav.

3. Read

/api/v1/record assembles the board payload for the current portal.

4. Act

/api/v1/act validates permissions and dispatches the requested operation.

5. Persist

Core modules write through Prisma and return compact API responses.

Portal Surface

Office

  • Dashboard, people, admissions, staff, school setup, timetable, fees, exams, roles, notices.
  • Phone tabs stay Desk, People, Staff, Fees, More.
  • Office-only admin work is permission gated in lib/permissions.ts.

Teacher

  • Desk, attendance, class, exams, timetable, inbox, notices, leave.
  • Phone tabs stay Desk, Attendance, Class, Exams, More.
  • Assigned/reporting scopes limit class, exam, timetable, and leave views.

Parent

  • Children, attendance, timetable, fees, examinations, papers, inbox, notices, profile.
  • Parents use /tests for examinations, not /exams.
  • Fee payment links route to Express public pay pages.

Student

  • Today, attendance, subjects, tests, papers, path, timetable, fees, profile.
  • Access is self-scoped by role grants.
  • Shared family boards render student and parent experiences where appropriate.

Backend Boundaries

Area Files Rule
Authentication server/index.ts, lib/login.ts, lib/auth-challenges.ts Use the existing token and challenge flows; keep portal and permission output consistent.
Reads lib/api-v1-record.ts, lib/data.ts, domain helpers Build role-aware payloads through recordPayload; do not add screen-specific REST routes for normal app reads.
Writes lib/run-act.ts, lib/core-actions.ts, lib/core-office.ts Add a new op for app mutations; enforce access through permission helpers.
Files lib/handle-upload.ts, lib/uploads.ts Use the existing upload, presign, complete, view, and /api/files/*rel route shape.
Public payments server/pay-html.ts, lib/pay-public.ts, lib/pay.ts Pay and invoice links must hit Express. School gateway keys live in SchoolConfig, not env files.
SaaS/admin site lib/anekio-site.ts, lib/saas-admin.ts, server/index.ts Marketing, admin CRM, SaaS billing, and subscription lock are Express-rendered surfaces.

Database Design

The database models group into school operations, academics, fees, staff, documents, admissions, and Anekio SaaS administration. Keep feature changes near the domain that owns the records.

Identity And Access

  • User, Role, and RoleGrant define portal access.
  • Permission keys are code-owned in lib/permissions.ts.
  • Scopes are SELF, ASSIGNED, REPORTS, and SCHOOL.

School Core

  • Teacher, Parent, Student, Class, and Subject.
  • Student add-ons, interests, class teachers, and teacher skills extend the people graph.
  • School sessions, holidays, rooms, periods, and timetable slots define operations.

Attendance And Staff

  • Attendance tracks student presence.
  • StaffMember, StaffDay, audits, and payroll runs track employee operations.
  • LeaveType, LeaveRequest, and SubstituteAssignment handle leave workflows.

Fees And Payments

  • FeeTemplate, FeeLine, FeeInvoice, and Payment.
  • SchoolConfig stores school payment settings and public website configuration.
  • Gateway methods include cash, UPI, Razorpay, Cashfree, BillDesk, bank, and cheque.

Academics And Documents

  • Exam series, exams, papers, evaluators, results, and audit rows drive marks workflows.
  • Templates, template versions, issued documents, and document events support document studio.
  • Contest, grant, and student path models support enrichment records.

SaaS Administration

  • SaasOrg, subscriptions, demos, follow-ups, onboarding tasks, and support tickets.
  • SaaS payments, invoices, audit events, pricing, email config, rules, and deliveries.
  • Subscription lock affects the app payload and hides school modules until renewal.

Database Change Workflow

Before Changing Schema

  • Create or identify the Jira ticket and document the planned schema change first.
  • Edit prisma/schema.prisma; this project uses prisma db push, not migrations.
  • Check whether seed data, demo exports, API serializers, permissions, and mobile screens need matching updates.
  • Do not hand-edit Anekio-demo-logins.* or mobile/.expo/types/router.d.ts.

After Changing Schema

  • Run npm run db:push for local schema sync.
  • Restart npm run api because lib/prisma.ts caches the Prisma client.
  • Verify API health with GET /health on port 4000.
  • Update Jira with files changed, verification performed, and any remaining notes.

When adding a new screen, add the permission in lib/permissions.ts, align lib/nav.ts, mobile/lib/nav-icons.ts, and mobile/components/office-boards.tsx, then route by nav key in mobile/lib/paths.ts.

Integration Rules

Metro And Express

App JSON goes through Metro on :8081. Metro proxies /api, /pay, and /i to Express on :4000.

Public Links

Public pay, invoice, verification, and document links are Express pages. Hosts ending in :8081 map back to :4000 for these flows.

Payment Secrets

School gateway keys are stored per school in SchoolConfig. Do not add them to .env or commit them. CRON_SECRET is the env exception.

Guardrails

Do Not Restore The Old Stack

Do not add Next.js, NextAuth, or /admin/reports pages. Existing NEXTAUTH_*, .next/, and stale href values are migration leftovers.

Preferred Change Shape

Keep app behavior in Expo, server behavior in Express, app reads in /api/v1/record, and writes in /api/v1/act.
